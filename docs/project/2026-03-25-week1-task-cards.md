# go-dfs v1 第 1 周任务卡

## 本周目标

把项目从“代码骨架”收口到“可继续迭代的可信基线”。

本周只做 4 件事：

1. 修绿基线
2. 收敛 README
3. 跑通本地多节点启动流程
4. 明确 v1 的能力边界

## 本周完成标准

完成本周后，应满足：

- `go test ./...` 通过
- `make build` 通过
- README 不再混淆“已实现”和“规划中”
- 有清晰的本地启动流程
- 能执行一次最小上传/下载验证

## Task 1：修复测试红灯

```text
任务：修复当前导致 `go test ./...` 失败的问题
为什么现在做：没有绿灯基线，后续任何功能收口都不可信
验收标准：
1. `go test ./...` 通过
2. 不通过关闭 vet 或删除检查来规避问题
3. 改动范围尽量小，只修复当前失败和相关明显问题
不做什么：
1. 不顺手重构整个启动流程
2. 不改业务逻辑语义
风险点：
1. 修日志或构建问题时误改运行行为
```

建议优先查看：

- `cmd/volume/main.go`
- `Makefile`

## Task 2：重写 README 的能力声明

```text
任务：把 README 改成与当前实现一致的版本
为什么现在做：作品项目的叙事必须和实际代码对齐，否则越写越虚
验收标准：
1. 区分“已实现”“可演示”“未实现/后续计划”
2. 删除或弱化无法证明的夸张表述
3. 补充最小运行路径和系统边界
不做什么：
1. 不补未来路线的细节设计
2. 不增加与当前代码不一致的承诺
风险点：
1. 文档仍然延续旧的过度承诺风格
```

建议优先查看：

- `README.md`
- `docs/testing-guide.md`
- `docs/benchmark-guide.md`

## Task 3：收口本地多节点启动流程

```text
任务：建立本地 `1 Master + 3 Volume` 的稳定启动方式
为什么现在做：没有统一运行闭环，就没有可复现演示，也没有可靠 smoke test
验收标准：
1. 启动命令清晰且可重复执行
2. 每个 Volume 的存储目录明确
3. Master 的元数据文件路径明确
4. 有清理旧数据和旧进程的方式
不做什么：
1. 不做 Docker 化
2. 不做部署到远程服务器
风险点：
1. 多进程残留导致假成功
2. 目录混乱导致测试互相污染
```

建议优先查看：

- `Makefile`
- `cmd/master/main.go`
- `cmd/volume/main.go`
- `configs/config.yaml`

## Task 4：补最小 smoke test

```text
任务：定义并落地一条最小 smoke test 流程
为什么现在做：单元测试不能证明整个系统真的能跑通
验收标准：
1. 能启动集群
2. 能上传一个文件
3. 能下载同一文件
4. 能校验内容一致
5. 失败时能给出清晰错误输出
不做什么：
1. 不覆盖所有故障场景
2. 不把它扩成完整集成测试框架
风险点：
1. 只验证 happy path，没有暴露真实运行问题
```

建议优先查看：

- `cmd/client/main.go`
- `internal/service/master.go`
- `internal/service/volume.go`

## Task 5：写出 v1 边界说明

```text
任务：定义当前 `go-dfs v1` 能力边界
为什么现在做：如果边界不写清，项目会继续失控扩张
验收标准：
1. 列出当前能稳定宣称的能力
2. 列出当前明确不支持的能力
3. 列出下一阶段只允许新增的一个方向
不做什么：
1. 不展开后续大而全路线图
2. 不写空泛愿景
风险点：
1. 重新把未来规划写成现状
```

建议输出位置：

- `README.md` 中一节
- 或 `docs/project/` 下单独文档

## 本周顺序

严格按下面顺序推进：

1. Task 1
2. Task 2
3. Task 3
4. Task 4
5. Task 5

不要跳过 Task 1，也不要在 Task 3 前扩展新功能。
