# go-dfs AI 协作清单

## 目标

在 `go-dfs v1` 的开发中，用 AI 提高实现速度，但不把需求定义、正确性判断和项目理解外包给 AI。

本阶段原则：

- 实现可以 Vibe
- 验收不能 Vibe
- 单元测试可以由 AI 起草
- 集成验证和最终结论必须由人来做

## 项目主线

当前只围绕 `go-dfs v1` 推进：

- `Master` 负责节点注册、心跳和文件位置管理
- `Volume` 负责本地存储和链式复制
- `Client` 负责上传和下载
- 本地 `1 Master + 3 Volume` 可稳定运行
- 上传、下载、心跳剔除等关键行为可验证

以下能力暂不纳入当前主线：

- `Raft`
- 自动数据迁移
- 复杂 quorum 语义
- `Prometheus` / `pprof`
- `Bitcask` 重构

## 分工边界

### 人负责

- 定义任务范围
- 写验收标准
- 判断系统行为是否正确
- 做黑盒验证
- 决定 README 中可以声明哪些能力
- 写每次任务完成后的复盘

### AI 负责

- 按任务卡实现代码
- 起草单元测试
- 生成脚本和辅助文档
- 解释代码路径和数据流
- 提供 bug 假设和重构建议

### 共同完成

- 集成测试脚本
- 架构说明文档
- 已知限制与后续演进列表

## 任务分级

### 绿档：可全 Vibe

适合内容：

- 构建修复
- 日志和 CLI 参数整理
- README 文案整理
- 脚本补齐
- 简单回归测试

要求：

- AI 可以直接实现
- 人必须 review diff 并运行验证命令

### 黄档：AI 实现，人主导验收

适合内容：

- 心跳逻辑
- 元数据持久化
- 链式复制
- 下载路径
- 一致性哈希接入
- smoke test

要求：

- 任务开始前必须先写验收标准
- AI 可以实现并补单元测试
- 人必须做黑盒验证并给出最终判断

### 红档：不允许全外包

适合内容：

- 一致性语义定义
- 故障恢复策略
- 系统边界声明
- 后续架构演进方向

要求：

- 人先给出方案或判断
- AI 只辅助整理、补充和审查

## 标准工作流

每个任务按以下 6 步执行。

1. 先写任务卡
2. 再让 AI 实现
3. 先看 diff，再看解释
4. 人工 review 主路径和失败路径
5. 跑自动化和黑盒验证
6. 写 3-5 行复盘

## 任务卡模板

```text
任务：
为什么现在做：
验收标准：
不做什么：
风险点：
```

## 给 AI 的实现模板

```text
任务：<任务名>
范围：只允许修改这些文件：<文件列表>
验收标准：
1. ...
2. ...
3. ...
不做：
1. ...
要求：
1. 先说明你理解的改动边界
2. 只实现当前任务，不扩 scope
3. 补必要的单元测试
4. 列出运行过的命令
5. 最后说明风险点和未覆盖情况
```

## 人工 Review 清单

每次至少回答下面 5 个问题：

1. 主路径是什么？
2. 失败路径是什么？
3. 测试验证了哪个行为，而不是哪个实现细节？
4. 有没有遗漏边界条件？
5. 如果线上出错，第一眼会看哪里？

## 验收要求

任何任务完成时，不能只接受“测试通过”。

至少要有：

1. 与任务相关的自动化验证命令
2. 一条黑盒验证
3. 一段人工结论，说明这次改动能证明什么，不能证明什么

## 复盘模板

```text
这次我确认了什么：
这次我还没真正理解什么：
AI 替我省掉了哪些机械工作：
如果下次不用 AI，我最可能卡在哪：
```

## 当前阶段的最低要求

在宣称 `go-dfs v1` 可用之前，至少满足以下条件：

1. `go test ./...` 通过
2. `make build` 通过
3. 本地可以稳定启动 `1 Master + 3 Volume`
4. 上传后可下载且内容一致
5. 节点不足时拒绝分配
6. 节点超时后能被 Master 剔除
7. README 的能力声明与实际行为一致
